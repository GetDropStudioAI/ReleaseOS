## Q-001 · M1 · How the EF migrations create the schema
Context: REOS-16/17. M1 asks for EF entities + fluent config (CHECKs, partial indexes, FKs) and a triggers migration.
Question: may migration `Schema` execute db/schema.sql's DDL verbatim instead of EF-generated DDL?
Options considered: (a) fluent-configure every CHECK/FK/index in EF (47 tables, ~100 CHECKs; drift risk between two definitions of the contract) / (b) run schema.sql's CREATE TABLE/INDEX text verbatim, map entities for columns and keys only, and assert with tests that migrated DDL text equals schema.sql and the EF model matches every column.
**Decided 2026-09-29 (best practice, on the user's instruction to use judgement): keep (b).** One definition of the contract, drift caught by tests.
Blocked: nothing. Built (b): `SchemaContractTests` proves table/index/trigger DDL is byte-identical to schema.sql and the model maps every column. Relationships are not navigations; FKs live in the database. Say if you want (a).

## Q-003 · M1 · Two sources of truth for a user's role
Context: authorization uses the role claim (IdP group map, `Auth:RoleMap`), but the separation-of-duties triggers read `Users.Role`.
Question: which wins?
Options considered: (a) just-in-time provisioning: on every sign-in upsert the `Users` row (email, display name, role from the claim), so both always agree / (b) admins maintain `Users.Role` and the claim is ignored / (c) both, with a mismatch refused.
Blocked: nothing. Built (a): `UserProvisioner` runs at sign-in (dev login and OIDC) and puts the `Users.Id` in a `uid` claim. Admin-edited roles are overwritten at the next sign-in; say if you want (b).
**Decided 2026-09-29: keep (a).** The identity provider is the single source of truth for who someone is and what role they hold; a role edited in the app would silently diverge from IdP group membership. Consequence: the Admin screen shows the role but role changes are made in the IdP group map (`Auth:RoleMap`).

## Q-004 · M1 · Is If-Match required?
Context: PROJECT_SCOPE §6 says "Mutations take If-Match: <Version>"; D8 says stale writes get 409.
Question: reject a mutation that has no If-Match header (428), or accept it and skip the check?
**Decided 2026-09-29: required.** Optimistic concurrency only protects anyone if clients cannot skip it. A versioned mutation without `If-Match` now gets 428 `{guard:"PreconditionRequired"}`. Config key `Api:RequireIfMatch` (default true) can relax it; the API test factory sets it false for older contract tests and a new test covers the 428.
Blocked: nothing. Was built optional; when present and stale -> 409 with the current row. Making it mandatory is a one-line change once the UI always sends it (M2).

## Q-006 · Password reset with MFA (REOS-59)
Context: requested 2026-09-29: "a way for a user to reset their password via MFA code or app". Sign-in today is OIDC (D12, OI-5), so the identity provider owns passwords and MFA. `Auth:Oidc:*` plus a dev-only fake login are all that exist.
Question: where should password reset live?
Options considered:
- (a) **Use the IdP's self-service reset** (Entra ID SSPR or equivalent): a "Forgot password" link to the IdP; MFA comes with it; near-zero code, no new secrets to protect, consistent with D12. Depends on your IdP offering it.
- (b) **Local accounts in this app**: password hashing (Argon2/PBKDF2), authenticator-app TOTP (RFC 6238) with recovery codes, rate limiting, audit rows, reset flow. Real scope: new tables (schema change), a security review, and it duplicates the IdP.
- (c) (b) plus emailed or texted codes: needs SMTP, which is off in v1 (OI-7), and an SMS provider.
Blocked: REOS-59 only. Nothing else waits on it.
**Answered 2026-09-29: option (a).** Built as config `Auth:PasswordResetUrl` (absolute https only, else ignored with a logged warning), exposed via anonymous `GET /auth/config`, shown as a link on the sign-in page. Reset and MFA are the identity provider's (e.g. Entra SSPR); the app stores no passwords or MFA secrets.

## Q-011 · M3 · Forecast rules the scope leaves open (REOS-31)
Context: PROJECT_SCOPE section 3 gives the forecast formula and the escalation thresholds; a few cases it does not settle. The handoff scenario (`r26-24-scenario.json`) pins the main path and passes exactly; these are the edges.
Question and what was built (all provisional, one place each in `RunForecasting` / `RunService`; say if any should change):
- **A step that has not started cannot start in the past:** its forecast start is the latest of its planned start, its dependencies' forecast ends and *now* (the text only names "now" for the running step's successors; a general floor is the same rule without the special case).
- **Skipped** is transparent (it ends when its dependencies end). **Failed** stops the forecast: everything after it, and the finish, are unknown and reported in `blockedByFailed`; no alert is raised on an unknown finish (the failure itself is the alert).
- **Rehearsal:** the plan and the window are shifted by the same D28 offset, so a rehearsal has its own deadline. Rehearsals never page anyone.
- **Late escalation** fires when a Live step *starts* 5+ minutes behind its plan (owner or owning team's members + all RTEs, level 1) and, at 30+ minutes, also the Release Managers (level 2). A step that is late because it has not started yet is REOS-37's timer (NotificationScheduler).
- **Rollback deadline crossing** notifies all RTEs and Release Managers once per run, the first time the forecast finish passes the deadline.
- Notification or push failures after a committed step are raised through `IAlertSink`, never swallowed and never undo the step.

## Q-012 · M4 · Go/No-Go rules the scope leaves open (REOS-33)
Context: PROJECT_SCOPE names the endpoints and D29 the expiry behaviour; a few edges are not settled.
**Decided 2026-09-30 (best practice; say if any should change):**
- **The latest decision is picked by `DecidedAt`** (also inside the Executing trigger), and timestamps have whole-second resolution, so a decision that is not strictly later than the latest is refused (`DecisionTooSoon`) instead of guessing an order.
- **Conditions can be added after the fact only to the latest GoWithConditions decision** (`NotLatestDecision` otherwise); decisions themselves never change. A superseding decision starts a fresh condition list.
- **Who closes a condition:** its owner or a Release Manager. Recording and adding conditions is Release Manager only (RTE has no Go/No-Go rights, PROJECT_SCOPE section 1).
- **A NoGo may carry `newTargetReleaseDate`; recording it does not move the train's target.** Moving the target stays the explicit `PATCH /trains/{id}` (audited, rebases gates), so one action never changes two things.
- Recording or closing bumps the train `Version` so open views go stale (409) and live clients refetch.
- Expiry notifications (owner + Release Manager, 1 h before) belong to REOS-37's scheduler.

## Q-035a · M4 · Evidence storage, size limit and config keys (REOS-35)
Context: PROJECT_SCOPE says "attachments stored outside `wwwroot`", 50 MB max, SHA-256 server-side; not settled: layout, config, what "too large" returns.
**Decided 2026-09-30 (best practice; say if any should change):**
- Config `Attachments:Directory` (default `data/attachments`, relative to the working directory like `Db:Path`, git-ignored) and `Attachments:MaxBytes` (default and ceiling 52,428,800, the schema CHECK; a larger value is clamped).
- Files are **id-named** (`<last 2 chars of id>/<id>`), not content-addressed: two uploads of the same bytes are two rows/files, so deleting one never affects another. `StoragePath` is stored relative and re-checked to stay under the directory on every read.
- The upload is streamed to `<dir>/.tmp/<guid>`, hashed as it streams, moved into place just before the DB commit, and removed if the commit or any later step fails. A cleanup that itself fails raises `IAlertSink` (`Attachments`/`UploadCleanup` or `DeleteCleanup`); a row whose file is missing raises `Attachments`/`FileMissing` on download and returns 404.
- Over the limit returns **413** `{guard:"AttachmentTooLarge", message}` (also from `Content-Length` before any byte is read); an empty file is 422 `AttachmentEmpty`.
- Multipart order: `entityType` and `entityId` fields **before** the `file` part, so a refused upload is refused unread. A `sha256` field, if sent, is ignored.
- File name is sanitised at upload (last path segment, control/bidi/reserved characters removed, at most 180 chars); the stored `ContentType` is the client's if it is a plain `type/subtype`, else `application/octet-stream`. Downloads always send `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store` and `X-Content-SHA256`.

## Q-036 · M4 · Close-out rules the scope leaves open (REOS-36)
Context: PROJECT_SCOPE names `:rehearsed-rollback`, the PIR auto-creation, `GET/PATCH /trains/{id}/pir` and `/trains/{id}/known-issues`, and the schema has the tables, but not who does what or the PIR/issue life cycles. **Decided 2026-09-30 (best practice; say if any should change):**

- **Q-036a Rollback attestation.** Attester = the acting RTE or Release Manager (existing `Plan` policy); the attestation is the train's `RollbackRehearsedAt/ByUserId`. Optional body `{runId, note}`: `runId` must be an *ended Rehearsal run of this train* (`InvalidRehearsalRun`), and it and the note go into the audit row (no schema column, so `db/schema.sql` is untouched). Evidence is optional at every risk tier: requiring a run would make the guard depend on data the schema does not enforce. Refused on a Complete or Aborted train (`TrainClosed`); attesting again replaces the earlier attestation and the audit row keeps what it replaced. `GET /trains/{id}/rollback-attestation` feeds the UI. Readiness already shows the `RollbackNotRehearsed` blocker.
- **Q-036b Who manages the close-out.** PIR (summary, schedule, hold, close, actions) and known issues: RTE, Release Manager and Governance Officer (403 for Viewers). An action can also be completed or reopened by its owner (`PirActionRole` otherwise). Accepting a known issue is a risk acceptance: Release Manager or Governance Officer only (`KnownIssueAcceptRole`). Exiting hypercare: RTE or Release Manager.
- **Q-036c PIR life cycle.** `Required -> Scheduled -> Held -> Closed` through action endpoints (`pir:schedule`, `pir:hold`, `pir:close`); `PATCH /trains/{id}/pir` edits only the summary. Holding needs a summary; closing needs the PIR Held and every action done (`PirActionsOpen`). Closed is final: summary, actions and status are read-only (`PirClosed`). `POST /trains/{id}/pir` starts a PIR with reason `Manual` for a Complete train that has none (a Successful close that later went wrong). `RollbackPerformed` is not created automatically: nothing in the scope says which event sets it. **Superseded 2026-10-22 by REOS-87 (Q-0870):** ending a Live run RolledBack creates it, aborting an Executing train creates one with reason `Aborted`, and a PIR may be started by hand on an Aborted train too. PIR writes do not bump the train Version (the PIR row has its own).
- **Q-036d PIR actions.** Text, an active owner and a due date that is not in the past when set (service clock); a done action is not edited (reopen it first). The list is ordered by due date.
- **Q-036e Known issues.** Allowed while the train is Gated, Executing or Complete (not Aborted) and hypercare has not ended. `PATCH` edits title, severity, workaround and reference only; `:accept` (Open -> Accepted, needs a workaround, `WorkaroundRequired`), `:resolve`, `:reopen` move the status. A Resolved issue is read-only until reopened.
- **Q-036f Hypercare exit.** `POST /trains/{id}:exit-hypercare` sets `HypercareExitAt/ByUserId`, needs a Complete train and no *Open* Critical or High issue (resolve or accept it first, `OpenKnownIssues`), and bumps the train Version. After it the known-issue log is frozen (`HypercareEnded`). The PIR is deliberately not a prerequisite: reviews normally happen weeks after hypercare ends.

## Q-037a · M4 · Reminders, escalation and the notification scheduler (REOS-37)
Context: PROJECT_SCOPE 5.5 lists the notices but not when a notice is "sent", how it is kept from repeating, or what "DueOn passed" means for a date. **Decided 2026-09-30 (best practice; say if any should change):**
- **Gate entered InProgress is sent by the scan, not from `GateService.StartAsync`.** The scheduler owns every notice, GateService stays untouched (REOS-34 edits that path) and a gate that became InProgress by any route (start, reopen, decertify) is caught the same way. Cost: up to `Notifications:ScanSeconds` (default 30) of delay. A reopened gate does not notify again (the dedupe key is unchanged).
- **Idempotence needs no schema change.** A notice is one `Notifications` row per (recipient, `Kind`, `EntityType`, `EntityId`, `EscalationLevel`); a scan only writes the rows that do not exist. A restart forgets nothing, and a recipient added later (new team member) still gets theirs. Kinds: `GateEntered`, `GateReminder`, `GateOverdue` (level 1 Release Managers, level 2 RTEs), `StepLate` (level 1 owner + RTEs, level 2 Release Managers; entity is the `StepExecution`), `ConditionExpiring` (level 0), `ConditionExpired` (level 1); entity types `StageGate`, `StepExecution`, `GoNoGoCondition`.
- **"DueOn passed" = the end of the DueOn calendar day in `Display:TimeZone` (D24).** Level 1 fires at the start of the next local day. **Level 2 fires when one whole business day has passed after the due day**: `AddBusinessDays(DueOn, 1)` is that business day (weekends and `Holidays` skipped), and level 2 is the start of the day after it. Due Fri 23 Oct: level 1 Sat 00:00, level 2 Tue 27 Oct 00:00 (Mon 26 Oct is the business day; if Mon is a holiday, Wed 28 Oct).
- **The 50% reminder** is measured from the latest `GateTransitions` row into InProgress (fallback `LastChangedAt`) to the due instant above; a gate entered after that instant, or already overdue, gets no reminder. Overdue notices apply to every unfinished gate (Pending, InProgress, Failed) of a Planning, Gated or Executing, non-archived train.
- **Step timer (the timer half of Q-011):** a `Scheduled` step of an open **Live** run whose planned start passed 5 min ago (owner or owning team's members + RTEs, level 1) or 30 min ago (Release Managers, level 2). Rollback-section steps never count (they only run when needed) and rehearsals never page. If a step later starts late, `RunService` still sends its own "started N min after plan" notice (different entity type), so a person can see both facts: not started, then started.
- **Conditions:** only the latest decision's open conditions of a non-closed train. 1 h before `ExpiresAt` the owner is told once; from `ExpiresAt` on the owner and all Release Managers are told once (D29). A scan that first sees a condition after `ExpiresAt` skips the 1 h notice.
- **Failure handling:** each rule (gates, steps, conditions) runs on its own; a failure raises `IAlertSink` and writes a `SyncAlerts` row (source `Notifications`, kind `DeliveryFailed`, fingerprint per rule so repeats bump `OccurrenceCount`), audited, and the first occurrence notifies RTEs and Release Managers in-app (that is also the live push, `NotificationCreated`). The next scan retries what failed. The `IAlertSink` registered in Program is still the logging one (M0 stand-in); the scheduler and the webhook sender write `SyncAlerts` themselves through `SyncAlertWriter`, so switching the sink later needs no change here.
- The first scan runs one interval after start (not at startup) since nothing is lost by waiting.

## Q-037b · M4 · Team webhooks and the inbox endpoints (REOS-37)
Context: PROJECT_SCOPE 5.5 says "optional team webhooks"; the schema has `Teams.WebhookDestinationId` and `WebhookDestinations(Url https only, Kind Teams|Slack|Generic)`. **Decided 2026-09-30 (best practice; say if any should change):**
- **Which notices go to a webhook:** those about a gate or step **owned by a team** with a destination, sent to that team once, together with the notice's first in-app row (so a scan never re-sends). Notices about conditions (user-owned) and role-addressed notices have no team channel. A team-owned entity whose team has no members and there are no role holders writes no in-app row and so sends no webhook (nothing to dedupe against).
- **Payload:** Teams and Slack `{"text": message}`; Generic `{kind, entityType, entityId, escalationLevel, message, trainId, at}`. No links or secrets.
- **Safety:** https only (`http` accepted only when the host environment is Development; the schema CHECK already forbids it); no credentials in the URL; no redirects; no private, loopback, link-local, CGNAT, multicast or reserved targets (IPv4, IPv6, IPv4-mapped) unless `Notifications:Webhooks:AllowPrivateTargets=true` (for an on-prem relay). The address is vetted before sending and again at connect time by the named client's `ConnectCallback`. The client ignores the system proxy (`UseProxy=false`) so the vetted address is the address used; a deployment that must go through an egress proxy needs a decision (allow-list the proxy, or set `AllowPrivateTargets` for it).
- **Bounds:** `Notifications:Webhooks:TimeoutSeconds` (10, max 60) per attempt, `MaxAttempts` (3, max 5), `RetryDelayMs` (500, growing per attempt); 5xx, 408, 429 and network errors retry, other 4xx do not.
- **Secrets:** the webhook URL (the token is in its path) is never logged, audited or put in an alert or notification; alerts carry the destination name, host and reason only, and transport exceptions are reported by type. Success writes one audit row (`WebhookDestination` / `Delivered`); failure raises an alert (source `Webhook`, kind `DeliveryFailed`, fingerprint = destination id). SMTP stays off (OI-7).
- **Inbox:** `GET /me/notifications` is newest first, `limit` 1-100 (default 50) and `offset`; `unread=true` filters. Marking someone else's notification is **403** `{guard:"NotYourNotification"}` (ids are random UUIDs, so 403 leaks nothing useful and is more helpful than 404); unknown id 404. `:read` is idempotent (an already-read row is unchanged, no new audit row); `:read-all` audits once with the count. Each item carries `trainId`/`trainTitle` when its entity resolves to a train, for deep links.
- **My work** (`GET /me/work`): items are mine if I own them or a team I belong to does (`via.kind` "me" | "team"). Open checklist tasks and unfinished gates (Pending, InProgress, Failed) of Planning/Gated/Executing non-archived trains; `Scheduled`/`Running` steps of open runs (Rehearsal included, `runMode` says which; `late` = Live, not started, 5+ min past plan); my open conditions of the latest decision; my undone PIR actions. Each list is sorted by due date; `overdue` compares a due date with today in `Display:TimeZone`.

## Q-038t1 · M4 · Train templates: who does what, and the edit endpoint (REOS-38)
Context: PROJECT_SCOPE lists `GET/POST /templates` and `POST /templates/{id}:approve` `:retire` but the permission table has no row for templates. **Decided 2026-09-30 (best practice; say if any should change):**
- **Draft create and edit: RTE and Release Manager** (the Admin policy, v1, D14/D32; the scope lists "train templates" among the admin and support screens). Everyone signed in can read. Editing a Draft is `PUT /templates/{id}` with the whole body (name, default risk, gates, steps, T-minus items) and `If-Match`; the child rows are replaced in one transaction. `PUT` was added because the scope names no edit route.
- **Approve and retire: Release Manager and Governance Officer.** An approval is a governance act, and the RTE who normally drafts is deliberately excluded. The role is checked by the endpoint and again by the service (`TemplateApproverRole`), like waivers.
- **No separation of duties** between author and approver: the docs do not ask for it and a Release Manager may draft and approve alone (a Governance Officer can only approve). Say if it should be required; it would be one audit lookup in `TemplateService.ApproveAsync`.

## Q-038c · M4 · Audit CSV export: format and the row cap (REOS-38)
Context: the scope says "Audit log | CSV | filtered events with before/after JSON" and scale is 100k audit rows. **Decided 2026-09-30:**
- **Format.** RFC 4180 through Sep (`Escape = true`: Sep does *not* quote by default), UTF-8 without BOM, header always present (also for an empty result), columns `Id, OccurredAt (UTC ISO), Actor, ActorUserId, Train, ReleaseTrainId, EntityType, EntityId, Action, BeforeJson, AfterJson`, newest first. **Line endings are LF, not CRLF** (Sep writes the platform newline; every mainstream parser and Excel accept it). Streamed in batches of 500, never buffered whole. `Content-Disposition: attachment; filename="audit-yyyyMMdd-HHmmss.csv"`, `Cache-Control: no-store`.
- **Formula injection (OWASP).** A cell that begins with `=`, `+`, `-`, `@`, tab or CR gets a leading single quote; only the first character matters. This applies to every text column, so a JSON cell is unchanged unless it starts with one of those characters (JSON objects start with `{`).
- **Row cap: 50,000 (`Audit:CsvMaxRows`).** An export never silently drops rows: when more match, the file holds the **newest** 50,000, response headers say `X-Audit-Truncated: true` and `X-Audit-Total-Rows: N`, and the file ends with one marker row whose `Id` cell reads `# truncated: 50000 of N matching events exported (newest first); narrow the filter (from/to) to export the rest` (a `#` first cell follows the scope's convention that `#` columns are skipped on import). Not truncated: `X-Audit-Truncated: false`. Chosen over a 422 because a partial file with a loud marker is more useful to an auditor than a refusal, and over chunked download links because the date filter already partitions. The key exists so a deployment can raise it. The CSV of a whole log at the scoped 100k rows is two exports by date.

## Q-043a · M6 · Token grammar and what blocks dispatch (REOS-43/44)
Context: PROJECT_SCOPE 5.2 says "unknown token = error; dispatch refused" and nothing about malformed braces. **Decided 2026-09-30 (best practice; say if any should change):**
- A token is `{`, an ASCII identifier, `}`. Names are **case-sensitive** (`{status}` is an error that suggests `{Status}`). Anything else between braces (`{}`, `{ Status }`, `{a-b}`), an unclosed `{` and a stray `}` are errors too (`MalformedToken`, `UnclosedBrace`, `StrayBrace`), each with line and column and, for a near-miss, a "Did you mean" suggestion (edit distance up to 2).
- **There is no escape for a literal brace** (no `{{`): a typo such as `{{Status}}` would otherwise print silently. If a message ever needs a literal brace it needs a decision here.
- Errored text stays in the preview as typed so the author sees where it is; `canDispatch` is false while `tokenErrors` is non-empty. REOS-45 must refuse on that.
- **Saving a template with token errors is allowed** (library entry and per-train copy); the responses carry `tokenErrors` and `valid`, the editor shows them, and dispatch is the gate. Rejecting the save would stop an author keeping unfinished work.

Values (never template text, except in Html) are escaped; the result is never rescanned, so a value containing `{Status}` prints as typed.
- **PlainText** (subjects, `mailto:`): verbatim values, `**` bold markers dropped from the template text, bullets `• `.
- **Markdown**: values have `\ ` * _ [ ] < > | ~` backslash-escaped and a leading `# - + =` on a line escaped (no headings, lists, links, images, raw HTML or tables can be injected); bullets are `- `; the gate table is a fenced block whose gate names cannot contain a backtick.
- **Html**: template text **and** values are HTML-escaped (`& < > " '`), `**x**` becomes strong (only from the template, never from a value), line breaks become `<br>`, the gate table is `<code>` lines.
- **JsonString**: the Markdown rendering, then the whole text escaped as JSON string content (no surrounding quotes), so the dispatcher can drop it between quotes of a Teams/Slack payload. Chosen over per-value JSON escaping because a template's own newlines would otherwise break the string.
- Control characters other than tab/newline are stripped from every value, CR and CRLF become newlines. The **subject** is rendered single-line as plain text (Html and Markdown callers still get a plain subject; JsonString keeps JSON escaping); a list in a subject joins with "; ".

## Q-039a · M5 · What an ExternalLink's key looks like, and what each system is asked (REOS-39)

## Q-039b · M5 · Where credentials and the Data Protection key ring live; the SSRF rules for connectors (REOS-39)

## Q-039d · M5 · 429 counter, backoff and what "consecutive" counts (REOS-40)
Context: the scope wants exponential backoff and an alert after 3 consecutive 429s, and "consecutive-429 counter" in `ConnectorState`, but the schema has only `ConsecutiveFailures`. **Decided 2026-09-30, without changing `db/schema.sql`:**
- `ConsecutiveFailures` counts consecutive failed cycles of **any** connector-wide kind (auth, unreachable, throttled). The **429 streak** is kept **in memory** per connector, so a restart starts counting again (worst case the alert comes 2 intervals later). Persisting it would need a column; say if it should.
- After the n-th consecutive 429 the connector is skipped until `now + min(max(base * 2^(n-1), Retry-After), one poll interval)` (`Sync:BackoffBaseSeconds`, default 30). A skipped cycle still counts as the poller being alive (heartbeat) but is not a clean cycle, so it resolves nothing.
- The alert is raised from the 3rd consecutive throttled cycle on (and repeats bump its count); any success or any non-429 outcome resets the streak.

## Q-039f · M5 · How alerts are keyed, scoped and resolved (REOS-40)
Context: the fingerprint is `hash(system, kind, key)` but the scope does not say what the key is. **Decided 2026-09-30:**
- **Connector-wide** failures (401/403 `AuthFailed`; timeout, network and 5xx `Unreachable`; `RateLimited`) use key `connector` and no train, so they show on the every-screen banner. The cycle **stops** at the first such failure (every link would fail the same way, and a bad credential should not be hammered), so one alert is raised **once per cycle**, however many links there are: 288 cycles = count 288.
- **Link-level** findings (`NotFound` 404 or an empty ServiceNow result; `ParseError`; every `Mismatch` rule) use the link id (mismatches `linkId:rule`) and the link's train. The rest of the cycle carries on. A cycle with only link-level findings is a clean cycle for the connector (`ConsecutiveFailures` 0, `LastSuccessAt` stamped).
- **Auto-resolve (5.3.8):** a clean cycle resolves the connector's three connector-wide alerts, and each link that read cleanly resolves its own `NotFound`, `ParseError` and no-longer-violated `Mismatch` alerts. Resolved rows keep their count and stay as history; a later failure opens a new row (the unique index is on open rows only). Removing a link closes its open alerts at once. A connector with **no links** completes an `Idle` cycle (heartbeat only): it proves nothing, so it resolves nothing and makes no call. A cycle that fails unexpectedly (a bug) raises `SyncEngine`/`Stalled` with key `cycle:{source}` and resolves on the next good cycle.
- Every raise and resolve pushes `SyncAlertRaised`; the in-app notice to RTEs and Release Managers is sent on the first occurrence only.

## Q-039g · M5 · Watchdog thresholds (REOS-41)
**Decided 2026-09-30:** the watchdog runs on its own timer (`Sync:WatchdogSeconds`, 60) and, for every **enabled** connector, raises `SyncEngine`/`Stalled` (key `poller:{source}`, no train) when no cycle has **completed** for 3 intervals. A cycle that failed against the ITSM still counts (the alert is about a dead poller, not a down connector). The interval is 5 min, except once a deployment window has been open for at least one slow interval, when the poller is on the 1-minute cadence and the threshold is 3 min (a window that has just opened keeps 15 min, because the last cycle may legitimately be 5 min old). The reference time is the later of the last completed cycle and the watchdog's own start, so a restart after downtime is not a stall until 3 intervals after it. `>=` 3 intervals alerts (a test at exactly 15 min). Recovery resolves the alert (history kept). With no `ConnectorState` row there is nothing to watch. `Sync:Enabled=false` stops both services. Links older than the same threshold render as `stale` (`GET /trains/{id}/links`); a never-synced link is "not yet synced", not stale.

## Q-051a · M7 · What a feed token is, and where "scope" lives (REOS-51)

## Q-051c · M7 · How feed events are identified and versioned (REOS-51)
**Decided 2026-09-30:** UID = `{entityId}-{kind}@releasemgmt` with kind `target` (train id), `window` (window id), `gate` (gate id), `step` (step id), `freeze` or `chill` (freeze window id); never derived from a date or a title. SEQUENCE = (row Version - 1) + (train Version - 1): row Versions only grow, so SEQUENCE never decreases and rises exactly when the row or its train was edited (moving the target date bumps the train and every gate). DTSTAMP and LAST-MODIFIED come from stored timestamps (train `UpdatedAt`, gate `LastChangedAt` when later, freeze `StartsAt`, which has no timestamp of its own), never the clock, so an unchanged database gives a byte-identical file (tested). A freeze is not edited but renewed as a new row (D29), so a renewal appears as a new event. Events are written in UID order. Content is titles and times only (no DESCRIPTION); a train's status is not in the SUMMARY so a status change does not rewrite every event.

## Q-051d · M7 · What is in each feed (REOS-51)
**Decided 2026-09-30:** all-trains and one-train feeds carry, for every non-archived, non-aborted train: the target date (all-day), the deployment window (timed, UTC), each gate's due date (all-day; DTEND is the next day, per RFC 5545), plus every freeze and chill (all-day range). My work = the token user's gates (owner user, or a team they belong to) that are not certified or waived, and their runbook steps (timed, from `PlannedStartAt` + duration), on trains that are Planning, Gated or Executing. The freezes feed is freezes and chills only. ## Q-051e · M7 · The anonymous feed endpoint (REOS-51)
**Decided 2026-09-30:** an unknown, revoked, malformed or over-long token, and a train feed for a train that does not exist, are the same bare 404 (the lookup is by SHA-256 of the presented value, then the hashes are compared again in constant time). ## Q-048a · M7 · Where a preview lives, and what commit re-checks (REOS-48)
Context: `ImportJobs` has no column for the file or the plan, and the schema is the contract. **Decided 2026-09-30:** `:preview` writes the `ImportJobs` row (Previewed) and stores the uploaded file plus a small plan file (`{jobId}.csv`, `{jobId}.plan.json`: mode, counts, a signature, the preview rows) in `Imports:Directory` (default: `imports` beside the database; outside `wwwroot`, never committed to the repository). `:commit` re-reads the file, checks its SHA-256 against the job, **re-plans it against the database as it is now inside the write transaction**, and refuses with 409 when the plan's signature differs (a target row's Version moved, a resolved owner/product/gate changed, or the train's Version moved: the same stale rule as the bulk parser), with 422 `ImportHasErrors` when the re-plan has errors (the `trg_Import_NoCommitWithErrors` trigger stays the backstop), and with 422 `DecertifyNotAcknowledged` when a new task lands in a Certified gate and `acknowledgeDecertify` is not true. ## Q-048b · M7 · CSV-injection escaping that round-trips exactly (REOS-48/49)
Context: PROJECT_SCOPE 9 says cells starting `= + - @`, tab or CR are prefixed with `'`. That alone is not reversible (`-5` and `'-5` would both come back as the same text). **Decided 2026-09-30:** export prefixes ONE apostrophe on those five characters **and on a cell that itself starts with an apostrophe**. Import removes exactly one leading apostrophe when it is followed by one of those five characters or by another apostrophe; any other leading apostrophe (`'tis`) is data. So `Unescape(Escape(x)) == x` for every string (tested over about 8,000 generated strings): `-5` exports as `'-5`, `'-5` as `''-5`, `'tis` as `''tis`; a hand-written `'=x` imports as `=x`. The unescape runs on every cell before it is validated, so a numeric column holding `'5` still fails with a readable message. The audit CSV (`/audit.csv`, REOS-38) keeps its own `Safe` helper unchanged (it does not double leading apostrophes); the audit grid under `/exports/audit.csv` uses the new rule.

## Q-048c · M7 · Audit and Version for imports (REOS-48)
Context: D27 says one AuditEvents row per service write; there are no owning services for most kinds (nothing creates trains or products yet), and the existing services each open their own transaction, so they cannot be composed into one all-or-nothing commit. **Decided 2026-09-30:** the import service writes the rows itself with the same semantics as the services: `Version` stamped on every changed row, `LastChangedByUserId`/`LastChangedAt` (from the injected clock) on rows that have them, and **one AuditEvents row per created or changed row** (`Action` `ImportInsert` / `ImportUpdate`, Before/After holding only the columns that changed; all columns for an insert; the train id set where the row has one) **plus one row per job** (`ImportJob` / `Commit`, counts, file name, SHA-256). Unchanged rows write nothing. A train whose products, gates, tasks or steps changed is bumped once per job (Version, UpdatedAt, LastChanged*), as BulkCommit does, so open previews go stale. Effects the triggers cascade (decertify) write their own audit rows with the actor from the task. An import never writes a Status column: Status-like columns (`Status`, `CurrentStatus`, `IsCompleted`, `CloseCode`, `CertifiedBy`, `SyncState`...) are header errors with their own message, and new trains are Planning, new gates Pending.

## Q-048d · M7 · Export files: BOM, line ends, `#` columns, XLSX cells (REOS-49)
**Decided 2026-09-30:** CSV is RFC 4180 via Sep, **CRLF** line ends, UTF-8 **with a BOM** (Excel reads non-ASCII text correctly only with it; the importer accepts it with or without). Each import grid exports its import columns in the importer's canonical text (ISO dates, `...Z` timestamps, owners as email or `@handle`, `;`-lists sorted), then `#`-prefixed read-only columns (`#Id`, `#Version`, and per grid `#Status`, `#DueOn`, `#IsActive`, `#Completed`, `#SyncState`, `#LastSyncedStatus`) which imports skip, so an unedited export re-imports as all-unchanged and an edited one imports only the edit. XLSX: ClosedXML, one sheet, bold frozen filtered header; whole-number columns and `#Version` are numeric cells, everything else is a text cell (format `@`) so `007`, `2026-11-13` and `=1+1` stay what they are. **ClosedXML treats one leading apostrophe as Excel's "quote prefix" (strips it and sets a flag), which would hide the OWASP prefix from every other reader**, so the writer adds one more and clears the flag: the stored text is exactly the CSV text. ## Q-050d · M7 · Worker mechanics: claiming, retries, crash recovery, files, alerts (REOS-50)
Context: rules 3, 4 and 8 and the "restart-safe" requirement. **Decided 2026-09-30:**
- `ExportWorker` (hosted) ticks every `Exports:PollSeconds` (5); `RunOnceAsync` is public and reads only the injected `TimeProvider`. It claims the oldest `Queued` job inside a write transaction (two workers cannot claim one job), marks it `Running` (attempt counted, start time from the clock), renders, and marks it `Done`. A job queued while the worker is running waits at most one tick.
- **Identical open request** (same train, kind, format and requester still Queued/Running) returns the existing job instead of a duplicate, so a double click is harmless. A Done job is never reused: evidence packs are regenerated on demand (scope section 9).
- **Crash recovery:** at startup every `Running` job is an orphan and is put back to `Queued`; while running, a job `Running` for longer than `Exports:StaleRunningSeconds` (300) is put back too. After `Exports:MaxAttempts` (2) attempts a job is **failed visibly** ("interrupted N time(s) ... out of attempts") with the alert instead. Every requeue and failure has its audit row. A Done job is never rewritten (a late `FailAsync` on it is a no-op).
- **Files:** rendered to `{Exports:Directory}/.tmp/{job}.{guid}.part` (default directory `exports` beside the database, i.e. `data/exports`; never under wwwroot; `**/data/exports/` added to the repository ignore file), the SHA-256 is computed over the file **as it is on disk**, then it is moved to `{id[^2..]}/{id}.pdf|zip` (id-named, relative path stored, `..` and rooted paths refused). Any failure deletes the temp and final file, so a failure leaves no file; the startup sweep clears `.tmp`.
- **Failure = Failed job + alert:** `ExportService.FailAsync` marks the job `Failed` with the readable error (also in `Parameters.error`) and raises `SyncAlerts` source `Export`, kind `ExportFailed`, fingerprint = the job id (so each failed job is its own alert; a repeat for the same job bumps the count), train id set, which also writes the audit row, notifies RTEs and Release Managers and pushes SignalR (`SyncAlertRaised`). A failure of the worker itself (database down) raises the same alert with key `worker`. Cancellation at shutdown leaves the job `Running` for recovery.
- A **download** re-checks the file: missing -> 404 and an `ExportFailed` alert (`file-missing:{job}`); wrong size, or (up to 32 MB) a SHA-256 that no longer matches -> 422 `ExportNotReady` and an alert, and the file is not served.
- Job audit rows (`ExportJob` Enqueue/Start/Complete/Fail/Requeue) carry the train id, so they appear in that train's audit log and in the pack's own audit extract, and each publishes `TrainChanged` (the train's Version does not change; clients just refetch).

## Q-053b · M8 · Antiforgery for cookie authentication (REOS-53)

## Q-SEC-C1 · Security review · A NAT64 prefix chosen by the network operator is invisible to the SSRF check (SEC-C1)
Context: `WebhookAddressPolicy` (used at save time and at connect time by the connector, team-webhook and comm-webhook clients) now judges IPv6 forms that carry an IPv4 address by that address: IPv4-compatible `::/96`, SIIT `::ffff:0:0/96`, NAT64 well-known prefix `64:ff9b::/96` and 6to4 `2002::/16`; the NAT64 local-use prefix `64:ff9b:1::/48` (RFC 8215) is always blocked, as are `100::/64` and `2001:db8::/32`. A public IPv4 address behind NAT64 or 6to4 stays reachable, so an IPv6-only host with DNS64 can still call Atlassian Cloud and ServiceNow. **Not decided:** a deployment whose NAT64 uses a **network-specific prefix** (any /96 the operator picks, RFC 6052) translates `<prefix>::10.0.0.5` to a private address, and the app cannot know the prefix. Options: (a) add a config list (e.g. `Security:Outbound:Nat64Prefixes`) whose embedded addresses are judged like the well-known prefix; (b) rely on network egress filtering at the translator (translators should not forward to non-global IPv4). Default today: nothing beyond the well-known and local-use prefixes; say which. A deployment that must reach a private IPv4 service through NAT64 on purpose sets `Sync:AllowPrivateTargets` (or the webhook keys), as for any private target.
**Decided 2026-09-30 by John (REOS-77): support the operator's NAT64 prefixes (option a).** Built: `Sync:Nat64Prefixes`, a list (`Sync:Nat64Prefixes:0`, `:1`, ... or one value separated by commas, semicolons or spaces) of /96 prefixes written like `2001:db8:64::/96`. An address inside one is judged by the IPv4 address in its last 32 bits exactly like `64:ff9b::/96`, before any other IPv6 rule (so a ULA or other prefix is judged by its IPv4, not blocked as ULA). Each value must be IPv6, exactly /96, host bits zero and bits 64-71 zero (RFC 6052); anything else **stops the start naming the key**. One list serves connectors **and** webhooks (team and comm), at save time and at connect time: the webhooks have their own allow-private switches but share the one address policy (`OutboundAddressPolicy`, a singleton over `WebhookAddressPolicy`), and the translator is a property of the network, so there is no separate webhook key. Context: Q-051e counted failed feed lookups per client address and answered 429 to that address after `Ics:MaxFailuresPerMinute` (60), **before** a presented token was checked. Behind a reverse proxy that does not forward the client address, every caller shares the proxy's address, so anyone who can reach the feed URL (anonymous by design) could block every user's calendar subscription for a minute at a time with 61 bad requests. **Decided 2026-09-30 (REOS-67), option (b):** the token is looked up first and a **valid token is always served**; only a failed lookup (unknown, revoked, malformed or over-long token, or a train feed for a train that does not exist) counts toward the brake, and only failed lookups are refused by it (the 62nd failure in a minute from one address, and every one after it that minute, is 429 instead of 404). A served feed neither counts nor is refused. Tokens are 256-bit, so the brake never protected against guessing; it bounds how often one address is told "no". Each refused request still costs one indexed hash lookup (the lookup has to run to know the token is not valid). Forwarded headers for a known proxy (option a) are configured separately since SEC-E5 and still make the brake per client. `ResourceInjectionTests.Strangers_guessing_feed_tokens_behind_the_same_proxy_address_do_not_lock_out_a_valid_calendar` is no longer skipped.

## Q-SEC-F1 · REOS-63 · Which live connections a sign-out closes, and the re-check interval
Context: an open SignalR WebSocket is authorised once, so it outlived sign-out, session expiry and deactivation (scan-authn section 3, Q-SEC-A5 (e)). **Built:** `HubConnections` tracks every hub connection by the `uid` claim and a session id that is now also a claim (`reos_sid`, with `reos_signedin`, stamped by `SessionLifetime.OnSigningIn`). Sign-out closes **that session's** connections only; the same user's other browsers and devices stay open (they reconnect anyway, and their own cookie is still valid). A refused cookie (absolute lifetime, signed out, inactive user) and an admin deactivation close at once; a deactivation closes **all** the user's connections. `HubSessionMonitor` re-checks every connection each `Realtime:SessionRecheckSeconds` (**default 30**) for an inactive or deleted user, a signed-out session and the absolute lifetime, which covers changes made outside the app (imports, database fixes). Cookies issued before this change carry no session id; their connections are matched by user. **Say if:** a sign-out should close every session of the user ("sign out everywhere"), or the interval should differ. The idle timeout is not enforced on an open connection: the cookie slides on the app's own minute polling, which the hub does not see.

## Q-SEC-F3 · REOS-65 · Reason codes for a refused organisation sign-in

## Q-069 · Health · What `/healthz` says about the poller and the watchdog (REOS-69)
**Decided 2026-09-30, provisional:** each loop is reported as `{state, lastCycleUtc, stalledAfterSeconds}`: `disabled` when `Sync:Enabled=false`; `running` with the UTC time its timer loop last finished a pass (null before the first); `stalled` when no pass has finished for **3 of its own intervals** (poller: 3 x `Sync:PollSeconds` = 15 min, counted from its first due pass, so `Sync:StartDelaySeconds` is not a stall; watchdog: 3 x `Sync:WatchdogSeconds` = 3 min) or its loop has ended while the app runs (logged at Error). An enabled loop that has stalled makes `/healthz` **503 `Unhealthy`** (a load balancer or service manager then sees it). A pass that failed against Jira or ServiceNow still counts: a down connector is a sync alert, not a dead poller. A manual "sync now" does not count (it proves nothing about the timer). The heartbeat is in memory, so a restart starts counting again. **Say if** a stalled loop should instead be reported without failing the whole probe (a 200 with `status: Degraded`).

## Q-081d · REOS-81 · What blocks removing a gate; what goes with it
**Built:** only a `Pending` gate (422 `GateNotRemovable` otherwise, naming its status), with no `GateTransitions` row (the log is append-only and a trigger would refuse the cascade anyway), and with no evidence attachment on the gate or its tasks, waiver, blocker, gate-linked communication template or external link (422 `GateInUse`, counted). ## Q-081e · REOS-81 · Editing a gate, and its position
**Built:** PATCH changes name, class, offset or due date, owner (setting one owner clears the other) and required-before. ## Q-081f · REOS-81 · A gate's due date, field limits and name uniqueness

## Q-0880 · REOS-88 · Contingency before the rollback deadline
**Built (proposal P1, advisory, no schema change):** from the plan alone, with the live forecast's terms: planned finish = latest planned end of a step outside the Rollback section; rollback deadline = window end − total planned Rollback minutes; planned execution time = earliest planned start of those steps to the planned finish (gaps count; Hypercare steps count, as they do in the forecast); spare = deadline − planned finish; **contingency = spare ÷ planned execution time**, rounded down. ## Q-108a · REOS-108 · Overview numbers: what each one counts
**Built (B2, `GET /api/v1/overview?from&to`, no schema change; say if any definition is wrong):**
- **Range.** `from` and `to` are UTC dates (D44), inclusive; `to` defaults to today (UTC) and `from` to the 14 days ending at `to`; at most 400 days, otherwise 400 `InvalidFilter`. Only *Deployment success*, the *daily completions* and the closed rows of the *activity* table use the range; every other number is the state now.
- **Open train** = Planning, Gated or Executing, and not archived (the REOS-85 definition).
- **Active releases** = open trains, with the count per status. Detail "Across N teams · M products": distinct teams that own a gate or checklist task of an open train, and distinct product names (trimmed, case-insensitive) bundled in one. A train has no team or services of its own (B3), so these stand in for the design's "8 teams · 42 services".
- **Running now** = Executing open trains. Detail: how many of them have a Live run in progress (the design's "2 production · 1 staging" needs environments, D42).
- **Need attention** = the readiness blockers of open trains plus the pending approvals. Readiness blockers = the Stream's `blockers` (`GET /trains`, the guards of each train's next hop, as `:advance` runs them), summed. Pending approvals = the Approval items below. Window and freeze conflicts are advisory (REOS-85) and are listed but not counted. **Known overlap:** a Go/No-Go still to record, and a Compliance gate ready to certify, are also a readiness blocker of their train, so each counts twice; say if the card should count each thing once.
- **Deployment success %** = Successful ÷ completed × 100 for trains that reached Complete with `ActualEndAt` on a UTC date in the range, computed as 100 − analytics M10's `change_fail_pct` (round half away from zero, one decimal), so the two never disagree. Archived trains count, as in M10; Aborted trains do not (they never complete). Null with the detail "No releases completed in the range" when none did. Detail: the change in percentage points against the previous period of the same length (↑, ↓ or →).
- **Daily completions** (throughput chart): one entry per UTC day of the range, zeros included, with the Successful, SuccessfulWithIssues and Unsuccessful completions of that day. They sum to the card's counts. At today's volume (a few trains a month) most bars are empty, as the mapping warned.
- **Attention items** (all on open trains, soonest due first; due times are UTC; a date-only deadline is due at the end of that day in `Display:TimeZone`, where business days are counted):
  - *Compliance gate to certify* (`CertifyGate`): a Compliance gate InProgress with at least one task, every task done and every earlier gate Certified or Waived, so only a Governance Officer's certification is missing. Due: the gate's due date.
  - *Waiver to approve* (`ApproveWaiver`): a waiver not yet approved on a gate that is not Certified or Waived. Due: the gate's due date.
  - *Freeze override to approve* (`GrantOverride`, id `{windowId}:{trainId}:{requesterId}`): an open override request from `FreezeService.OpenRequestsAsync` (an audited `RequestOverride` stays open until a Grant/Renew names its requester for that window and train: the SEC-A1 rule), for a freeze that has not ended. Due: when the freeze starts.
  - *Go/No-Go to record* (`RecordGoNoGo`): a Gated train with no decision, or whose latest decision is No-Go. Due: when its deployment window opens, otherwise the end of its target date.
  - *Go condition to close* (`CloseCondition`): an open condition of the train's latest decision (a later decision replaces the earlier one's conditions, as in `GET /approvals` and My work). Due: its expiry.
  - *Gate failed*: a gate with status Failed. Due: the gate's due date.
  - *Change window conflict* (REOS-85, same match and buffer): one item per pair of trains, on the train whose window opens first, until both windows have ended. Due: when that window opens.
  - *Freeze conflict*: the train's window overlaps a **Freeze** (a Chill only warns, so it is left out) that covers the train (no product pattern, or a product matches it), the overlap has not ended, and no override for that freeze and train lasts to the end of the overlap. Due: when the overlap starts.
  The kind names and ids are those of REOS-94's `ApprovalQueueService`, so one map serves the Overview and Approvals screens. The overview is workspace-wide, not per person: who may act is named on each item (`actionBy`); the per-person queue is B1 (`GET /approvals`, REOS-94).
- **Release activity rows**: the open trains (soonest window, or target date when there is none, first), then the trains that completed or were aborted in the range (latest first; Aborted by its last change, as the Stream does); archived trains never. Each row has the status, a design status (Running = Executing; Blocked = Planning or Gated with a failed gate; Planned = other open trains; Successful = Complete Successful or SuccessfulWithIssues, with `closeCode` kept; Failed = Complete Unsuccessful or Aborted), the window, the end time, the product count and the readiness blockers. Owner, team and environment have no source until B3 and D42.

## Q-1072 · REOS-110 · Deployments, events and the push ingest API
**Built to the following; say if any is wrong:**
- **Keys**: `POST /api/v1/ingest-keys {name}` (Admin) returns the secret once (`rk_` + 43 base64url characters, 256 bits). Only its **SHA-256** is stored. CLAUDE.md rule 11 says credentials live in Data Protection or the OS secret store, never in SQLite; a hash is not a credential (nothing in the database can be used to call the API), and calendar tokens already work this way. The cost is that a lost key is replaced, not recovered. Sent as `Authorization: Bearer` or `X-Api-Key`. A cookie session is not accepted on the ingest routes (401 for every role).
- **Endpoints**: `POST /api/v1/ingest/deployments` (create 201, update or replay 200) and `POST /api/v1/ingest/events` (the story says "`/events`"; the deployment is named in the body, `deploymentExternalId`, so one route serves every deployment; up to 100 events of at most 2 000 characters per call). Deployments are identified by the tool's `externalId` (unique per workspace); events by an optional `externalId` per deployment. Replays change nothing and write nothing.
- **A new deployment needs** `serviceKey`, `environment` (by name) and `releaseVersion`; the service must be in the catalog and the environment must exist (neither is created on the fly: the catalog is managed, D42), otherwise 422 `UnknownService` / `UnknownEnvironment`. `releaseKey` links it to a release (422 `UnknownRelease`), and to that release's open **Live run**, if there is one when it is linked. An existing deployment keeps its service, environment and version (422 `DeploymentIdentityMismatch` otherwise).
- **States** Queued, Running, Paused, Successful, Failed, RolledBack, moved along `DeploymentStates.CanMove` (11 moves) with `trg_Deployment_Transition` as the backstop; a deployment may be *created* in any state (a tool reporting after the fact). A late or out-of-order push of an earlier state is 422 `IllegalDeploymentTransition` naming the current state: it is not silently ignored (rule 8). A deployment that becomes Successful with no stated traffic is at 100 %. Strategies Rolling, Canary (steps: 1 to 20 rising percentages), Atomic.
- **Audit**: every write is one `Deployment` / `DeploymentEvent` row, actor system, the key's id and name in the row; an event call is one row however many events it carries. A bad key is a host-wide `IngestKey/Rejected` row (address and reason, never the key), bounded per address (see the runbook, section 14).
- **Limits**: per key 100 calls/s, burst 200 (`Ingest:RequestsPerSecond`, `Ingest:Burst`); per address 30 refused keys a minute (`Ingest:FailedKeysPerMinute`), 10 of them audited (`Ingest:RejectionAuditsPerMinute`); beyond either, 429 (a valid key from an address that has used up its refused-key budget waits too: deliberate). `IngestKeys.LastUsedAt` is written at most once a minute and does not bump the Version.
- **Event order**: `DeploymentEvents.Id` is an auto-increment integer, like `AuditEvents`, an exception to rule 6 (UUIDv7): events arrive many to the second, the timestamps have one-second resolution, and a UUIDv7 does not order within a millisecond. Events are listed by the tool's `OccurredAt`, then arrival.
- **Live**: `DeploymentChanged(id, version, trainId)` to the workspace's group after the commit; none for a replay. Clients refetch `GET /deployments/{id}`.
- **Load**: the acceptance test sends 50 events/s for 3 s next to a reader of `GET /trains` and checks both p95s against generous bounds; a longer run is `REOS_INGEST_LOAD_SECONDS` (docs/LOAD_TEST.md section 6).
- **Not built (later stories)**: metric samples, threshold breach detection and automatic rollback; the control webhooks (pause, promote, rollback); the Orchestration and Deployment monitoring screens; Admin screens for keys, environments and the catalog.

## Q-116a · REOS-116 (RT1) · Release types on every release, and per-type templates
**Built to the following; say if any is wrong.** What was already there from REOS-107 (the `ReleaseTypes` table, `ReleaseTrains.ReleaseTypeId`, the service, `/release-types`, seeding at start, the Releases type filter and column, the CSV `ReleaseType` column) is kept; this story adds what was missing. - **"Cannot create a release without a type", service and trigger.** `POST /trains` and the CSV import refuse a missing type with 422 `ReleaseTypeRequired` ("Choose a release type: every release has one…"); a release cannot lose its type (`PATCH /trains/{id}/release` with an empty type: the same 422). `trg_Train_TypeRules_Insert` is the backstop. **Judgement call:** the rule applies once the workspace has any release type (archived ones count), so a database opened before the app seeded the types, and a workspace with no types at all, still accept a typeless release. Without that the many contract tests that insert rows by SQL (and every database restored from before 008) would be refused with no type to give. The app seeds every workspace at start and when it is created, so in a running system the rule always holds. `ReleaseTypes:SeedAtStart` (default `true`) turns the start-up seeding off; the Api contract tests set it `false` (their SQL fixtures have no types) and the tests of this rule set it `true`. Say if the trigger should refuse unconditionally.
- **Existing releases become Production, in the app, not the SQL.** At start a release without a type gets its workspace's type named Production (name compared ignoring case); a workspace that renamed Production gets a type called Production added for them. One `ReleaseFields` audit row per release (system actor, reason in the row), `Version` and `LastChangedAt` stamped, idempotent. Upgrade 008 itself only adds columns and triggers, because ids are UUIDv7 and audit rows come from the services (CLAUDE.md rules 3 and 6). Say if you want the backfill in the script as well.
- **New workspaces are seeded** with Beta, CERT, PenTest Cert and Production right after `POST /workspaces` creates them (its own transaction: the workspace being created is not the request's, and the workspace boundary refuses a row for another one). If that second step failed, the start-up seeding repairs it. Audited (`ReleaseType` `Seed`).
- **Beta numbering (D48).** Which type is "Beta" is data, not its name: `ReleaseTypes.IsBeta` (the seeded Beta has it; a planner can flag another type, or unflag one that no release uses; locked while releases use the type, in the service and by trigger). An existing Beta-typed release from before has no number until someone sets one; edits that do not touch the type or number are not blocked by that. A clone keeps the type and number (the person changes the number for the next Beta; "create the next release in the chain" is RT2). CSV: optional `BetaNumber` column, same rules.

## Q-118a · REOS-118 (RT3) · Clients and segments (Standard, On-Demand with a CERT environment)

- **"Only On-Demand clients have a CERT environment" is a rule in both directions.** A Standard client with an environment is refused, and so is an On-Demand client **without** one ("On-Demand clients have a CERT environment", D47). The service answers 422 `ClientInvalid` with a readable message; `trg_Client_SegmentRules_Insert/Update` is the backstop (a `DbRule` 422 for a write around the service). **Say if** an On-Demand client may exist before its CERT environment is known (the trigger and the screen would then drop the second half of the rule).

Column absent: a Standard row ends with no environment, an On-Demand row keeps the one it has (a new On-Demand row without one is an error on that row). Upsert updates segment and environment; the name's case is not changed by a file (it is the key). An archived client updated by a file stays archived. Planners import (the Plan policy, as trains); a Viewer gets 403. One `Client` audit row per created or changed row (`ImportInsert`/`ImportUpdate`) plus the job's row, as every kind.
